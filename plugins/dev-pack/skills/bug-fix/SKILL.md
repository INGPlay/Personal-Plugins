# 버그 수정 (Bug Fix)

잘못된 동작을 바로잡는 표준 절차. 핵심은 **먼저 재현하고, 근본 원인을 잡는 것**이다. 증상만 가리는 수정은 재발하거나 다른 곳을 깨뜨린다.

## 절차

1. **코드베이스 탐색** — `dev-pack:codebase-exploration` 스킬을 따른다. 문제가 나는 코드 경로와 관련 심볼·호출 관계를 파악한다.
2. **재현 + 근본 원인 파악** — 먼저 버그를 재현한다(테스트·실행·로그). 재현하지 못하면 무엇을 고쳤는지 판단할 수 없다. 재현되면 표면 증상이 아니라 **진짜 원인**을 찾는다 — 왜 그 값/상태가 되는지 흐름을 거슬러 올라간다. **전에는 되던 동작이 깨진 회귀라면, 코드를 읽기 전에 `git log -S<심볼>`·`git blame`으로 동작이 바뀐 커밋부터 찾는다** — 대개 그게 최단 경로다. 원인이 불명확하면 추측 수정 대신 로그·중간값으로 좁힌다.
3. **버그 수정** — 원인을 최소 범위로 고친다. 같은 클래스의 버그가 다른 곳에도 있는지 함께 확인하되, 무관한 리팩터링은 섞지 않는다.
4. **검증** — 통과 기준은 명확하다: **2단계의 재현 케이스가 사라지고, 나머지가 그대로일 것.** (a) 재현 케이스가 이제 통과하는지 확인하고, (b) 회귀를 막을 테스트를 추가하거나 기존 테스트를 돌린다. build/lint/test를 직접 돌리고 `/run`으로 실제 동작도 본다. 원인을 못 고치고 증상만 가린 것은 아닌지 스스로 점검한다. 보안 관련이면 `/security-review`도 직접 실행한다(호출 가능).
   **문제가 나오면 3단계로 돌아가 고치고 다시 검증한다. 통과 기준을 만족할 때까지 3~4단계를 반복한다.**
5. **커밋** — 검증을 통과하면 `dev-pack:commit` 스킬로 커밋한다(`fix:` 타입). 원인이 자명하지 않았다면 커밋 본문에 왜 그런 버그였는지 남긴다.
6. **코드 리뷰 인계** — 커밋까지 끝냈으면 **사용자에게 `/code-review` 실행을 요청하며 마무리한다.** 이 스킬은 사용자만 호출할 수 있어 Claude가 대신 돌릴 수 없다. 재현 케이스가 사라졌다는 확인과 원인·수정 내용을 한 줄로 요약해 함께 전달한다. 지적이 나오면 고친 뒤 **별도 커밋으로 남기는 것을 기본으로 한다.** 지적이 HEAD 커밋 하나에만 걸려 있고 아직 push하지 않았다면 `--amend`로 합쳐도 되며, 어느 쪽으로 할지는 사용자에게 확인한다. **push는 사용자가 명시할 때만 하고, 리뷰 전이라면 아직 리뷰를 받지 않은 커밋임을 먼저 알린다** — push한 뒤에는 `--amend`를 쓰지 않는다.

## 유의점

- **재현을 건너뛰지 않는다.** 재현 없이 고치면 "고쳤다"고 보고할 근거가 없다.
- 회귀 테스트를 남기면 같은 버그의 재발을 막는다 — 가능하면 4단계에서 추가한다.
- 원인을 찾지 못한 채 임시방편(우회)으로 넘어가야 한다면, 그 사실과 한계를 명확히 보고한다.
