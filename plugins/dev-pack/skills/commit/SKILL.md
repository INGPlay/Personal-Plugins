# 커밋 (commit)

이 프로젝트의 커밋 메시지 형식에 맞춰 변경사항을 커밋한다.

## 커밋 메시지 형식

간단한 변경(단일 목적, 한 줄로 설명 충분)은 제목만:
```
type: 한국어 요약
```

여러 파일/여러 이유가 얽혀 있거나 왜 바꿨는지 설명이 필요한 변경은 본문을 추가:
```
type: 한국어 요약

- 변경 내용 1
- 변경 내용 2 (필요한 이유)
```
본문은 무엇을 바꿨는지 나열하는 데 그치지 않고, 자명하지 않은 이유(왜 이렇게 했는지)가 있으면 함께 적는다. diff만 봐도 알 수 있는 내용은 굳이 본문에 반복하지 않는다.

### type 종류
| type | 의미 |
|---|---|
| feat | 기능 추가 |
| fix | 버그 수정 |
| docs | 문서 |
| refactor | 리팩터링 |
| test | 테스트 |
| chore | 설정·잡무 |

### 예시
- `feat: 관리자 목록 검색 추가`
- `fix: 로그인 401 토큰 갱신 처리`
- `chore: ESLint 규칙 추가`

## 여러 커밋으로 분리

변경사항이 서로 다른 목적/도메인을 섞고 있으면 하나의 커밋으로 묶지 말고 논리 단위로 나눠 여러 번 커밋한다 (예: 기능 추가 + 무관한 리팩터링, 서로 다른 도메인 수정). 파일 단위가 아니라 **논리적 변경 단위**로 나눈다 — 한 커밋에 여러 파일이 걸쳐도 하나의 목적이면 묶는다. 분리 여부와 각 커밋 그룹은 알아서 판단하고 진행하되, 각 커밋을 만들 때마다 무엇을 묶었는지 한 줄로 보고한다.

## 절차
1. `git status`, `git diff`로 변경 내용을 확인한다. 이때 **이미 staged된 파일이 있는지 함께 본다** — 있으면 그 파일이 첫 커밋에 섞여 들어가므로, 이번 커밋 그룹에 속하지 않는 것이 staged 상태면 사용자에게 알리고 어떻게 할지 물어본다.
2. 변경 파일 중 민감 파일(`.env`, `application-*.yml`, `application-*.properties`, `*credential*`, `*secret*`, 키/인증서 파일 등)이 포함되어 있으면 add하지 않고, 나머지 파일만으로 커밋을 진행할지 전체를 중단할지 사용자에게 물어보고 답을 받은 후 진행한다.
3. 변경 내용을 논리 단위로 그룹핑하고, 그룹별로 적절한 type과 커밋 메시지(필요 시 본문 포함)를 작성한다.
4. 그룹별 대상 파일만 명시적으로 `git add`한다 (`git add -A` 금지).
5. 별도 확인 없이 바로 `git commit`을 실행한다. 제목만이면 `-m`, 본문이 있으면 heredoc으로 전체 메시지 전달:
   ```bash
   git commit -m "type: 한국어 요약"
   ```
   ```bash
   git commit -m "$(cat <<'EOF'
   type: 한국어 요약

   - 변경 내용 1
   - 변경 내용 2 (필요한 이유)
   EOF
   )"
   ```
   Co-Authored-By 트레일러는 붙이지 않는다.
6. 여러 커밋으로 나누는 경우, 중간 그룹에서 커밋이 실패하면 이미 만든 커밋을 되돌리지 않고 그 자리에서 중단한다. 어떤 그룹까지 커밋됐고 어떤 그룹이 실패/미처리 상태인지 사용자에게 보고한다.
7. 모든 커밋 완료 후 `git log --oneline -n {커밋수}`와 `git status`로 결과를 확인하고 짧게 보고한다 (커밋별 메시지 요약 + 파일 목록).
8. 변경사항이 없으면 커밋을 만들지 않는다.
9. 절대 자동으로 push하지 않는다. push는 사용자가 명시적으로 요청할 때만 수행한다.
