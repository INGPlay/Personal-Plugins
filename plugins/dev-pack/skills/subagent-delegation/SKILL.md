# 서브에이전트 위임 (Subagent Delegation)

메인 세션은 **오케스트레이터**로서 태스크를 나누고, 맡기고, 결과를 판정하고, 통합한다. 기능 코드는 직접 쓰지 않는다. 구현은 `dev-pack:implementer`가 태스크마다 격리된 워크트리에서 하고, 검토는 `dev-pack:task-reviewer`가 한다. 메인 컨텍스트에는 계획·판정·통합 결과만 남기는 것이 목적이다.

## 언제 쓰는가

- **쓴다:** 설계 결과 파일 소유가 겹치지 않는 태스크 2개 이상으로 나뉘는 작업. 호출하는 절차들은 이 기준을 따른다.
- **쓰지 않는다:** 한두 파일로 끝나는 작업, 태스크끼리 같은 파일을 계속 주고받아야 하는 작업, 아직 원인을 찾지 못한 버그(원인 추적은 맡기기 전에 태스크를 정할 수 없으므로 메인 세션에서 끝낸 뒤 수정만 맡긴다). 이런 작업은 호출한 절차대로 메인 세션에서 직접 구현한다.

## 절차

1. **사전 점검** — 다음 스크립트를 돌린다(아무것도 바꾸지 않는다):
   ```bash
   bash "${CLAUDE_SKILL_DIR}/scripts/preflight.sh"
   ```
   - `worktree.baseRef`가 `head`가 아니면 워크트리가 원격 기본 브랜치에서 분기해 지금 작업을 보지 못한다. 위임을 멈추고, 설정 파일(`.claude/settings.local.json` 권장)에 `"worktree": {"baseRef": "head"}`를 넣을지 사용자에게 확인한다. 거절하면 메인 세션에서 직접 구현하는 것으로 돌아간다.
   - 커밋 안 된 변경은 워크트리로 넘어가지 않는다. 위임할 작업의 전제가 되는 변경이면 먼저 커밋할지 사용자에게 확인한다.
   - `.claude/worktrees/`가 gitignore되지 않았다면 사용자에게 알린다(위임은 진행할 수 있다).
   - 워크트리는 추적 파일만 체크아웃한다. 스크립트가 gitignore된 설정 파일(`.env` 등)을 찾았는데 `.worktreeinclude`가 없으면, 테스트에 그 파일이 필요한지 판단해 `.worktreeinclude`를 만들지 사용자에게 확인한다. 의존성(`node_modules` 등)은 implementer가 워크트리에서 설치한다.
2. **태스크 분해** — 호출한 절차의 탐색·설계 결과를 근거로 태스크를 나누고, 세션 스크래치패드(없으면 OS 임시 디렉터리)에 `delegation-<slug>.md`로 계획을 적는다. 태스크마다 다음을 적는다:
   - **목표:** 무엇을 만들거나 바꾸는지 한두 줄로 적는다.
   - **소유 파일:** 이 태스크만 수정하는 파일. 다른 태스크와 겹치면 태스크를 합치거나 다른 웨이브로 나눈다.
   - **인터페이스:** 다른 태스크가 의존하는 시그니처·데이터 형태를 정확한 값으로 적는다. 구현자가 추측하게 두지 않는다.
   - **통과 기준과 확인 방법:** 돌려서 확인할 수 있는 형태로 적는다(예: "`npm test -- auth` 초록 + `POST /login`이 401 대신 200"). 기준을 이렇게 적을 수 없으면 태스크가 덜 정의된 것이다. 나누거나 사용자에게 묻는다.
   - **하지 않을 것:** 범위 밖이라 손대면 안 되는 것.

   의존 관계로 태스크를 **웨이브**로 묶는다. 한 웨이브 안의 태스크는 서로 독립적이어야 하고, 한 웨이브는 최대 4개로 한다. 테스트가 DB·고정 포트처럼 공유 자원을 쓰면 병렬 실행이 서로 간섭하므로, 그런 태스크는 같은 웨이브에 넣지 않는다. 같은 종류의 작은 수정이 여러 파일에 반복되면 태스크 하나로 묶는다.
3. **계획 승인** — 웨이브·태스크·통과 기준을 표로 보여 주고 AskUserQuestion으로 승인받는다. 선택지에는 "메인 세션에서 직접 구현"을 함께 둔다. 위임은 태스크마다 워크트리·리뷰 비용이 들기 때문에 작업이 작으면 직접 하는 편이 낫다. 승인 전에는 구현을 맡기지 않는다. 이 승인이 사용자가 개입하는 주된 지점이다.
4. **웨이브 실행** — 웨이브마다 다음을 반복한다.
   1. 기준 커밋(`git rev-parse HEAD`)을 계획 파일에 적는다. 작업 트리가 깨끗한지 다시 확인한다.
   2. 웨이브의 태스크마다 `dev-pack:implementer`를 **한 메시지에서 동시에** 띄운다. 프롬프트에는 그 태스크 항목 전문, 앞 웨이브에서 확정된 인터페이스, 저장소의 build·test 명령만 넣는다. 세션의 지난 대화나 다른 태스크의 경과는 넣지 않는다. 동시에 띄운 implementer는 백그라운드에서 돌기 때문에 권한 확인 창을 띄우지 못하고, 허용되지 않은 명령은 바로 거부된다. 프롬프트에 넣은 build·test·git 명령이 권한 설정에서 허용되어 있는지 먼저 확인하고, 허용되어 있지 않으면 사용자에게 허용을 요청하거나 그 웨이브를 하나씩 포그라운드로 돌린다. 모델은 태스크에 맞춰 고른다: 명세가 완전한 기계적 작업은 가벼운 모델, 여러 파일을 엮거나 판단이 필요하면 표준 이상.
   3. 보고를 받으면 상태별로 처리한다. `NEEDS_CONTEXT`는 빠진 정보를 채워 SendMessage로 재개한다. `BLOCKED`는 원인을 보고 맥락 보충, 더 강한 모델로 새로 띄우기, 태스크 분할 중 하나를 고른다. 원인이 권한 거부라면 포그라운드로 다시 띄운다. 같은 조건으로 그대로 다시 시키지 않는다.
   4. `DONE`인 태스크마다 `dev-pack:task-reviewer`를 띄운다. 태스크 항목 전문, 기준 커밋, 태스크 브랜치, implementer의 검증 증거를 넘긴다. 리뷰어에게 특정 지적을 하지 말라고 미리 정해 주지 않는다. 독립적인 리뷰는 동시에 띄운다.
   5. **수정 루프** — 스펙 ❌이거나 Critical·Important 지적이 있으면 그 지적을 그대로 implementer에게 SendMessage로 보내 고치게 하고, 고친 부분만 다시 리뷰받는다(재검토에는 이전 지적 목록과 직전에 검토한 커밋을 넘긴다). Minor 지적은 계획 파일에 적어 두고 루프에 넣지 않는다. 최대 3회까지 돈다. 3회 뒤에도 남은 지적은 오케스트레이터가 판정해 `판정: <결정> — <이유> — <틀렸을 때 비용>` 형식으로 계획 파일에 남긴다. 다음 태스크가 그 위에 쌓이는데 어느 쪽이 맞는지 판단할 근거가 없으면 사용자에게 묻는다. 지적을 조용히 버리지 않으며, 메인 세션이 직접 고치지도 않는다. implementer를 재개할 수 없으면 새 implementer를 띄우고, 프롬프트에 태스크 항목·지적 목록과 함께 "기존 태스크 브랜치 `<브랜치>`를 `git cherry-pick HEAD..<브랜치>`로 가져와 이어서 작업하라"고 적는다. 이후에는 새 브랜치를 태스크 브랜치로 쓴다. 기존 브랜치와 워크트리는 계획 파일에 적어 두고 7단계에서 함께 지운다.
   6. **통합** — 리뷰를 통과한 태스크 브랜치를 계획에 적은 순서대로 현재 브랜치에 `git cherry-pick HEAD..<태스크 브랜치>`로 가져온다. 범위를 `HEAD..`로 잡아야 rebase한 브랜치에서도 그 태스크의 커밋만 가져온다. 충돌이 나면 `git cherry-pick --abort` 후 그 implementer에게 현재 브랜치로 rebase하라고 SendMessage로 재개한다. 충돌 해결로 코드가 바뀌었으므로 다시 가져오기 전에 `dev-pack:task-reviewer`에게 현재 `HEAD`를 기준 커밋으로 넘겨 재검토받고, 통과하면 rebase된 브랜치를 같은 명령으로 가져온다.
   7. **웨이브 검증** — 통합한 결과에서 build·test를 돌린다. 실패 원인이 한 태스크 안에 있으면 그 implementer를 재개해 고치게 하고 다시 통합한다. 태스크끼리 맞물려 깨졌다면 수정 태스크를 새로 정의해 작은 웨이브로 한 번 더 돈다. 통과하면 그 웨이브의 워크트리와 브랜치를 지운다(`git worktree remove <경로>`, `git branch -D <브랜치>`). 지우기 전에 `git cherry HEAD <태스크 브랜치>` 출력에 `+`로 시작하는 줄이 없는지, 즉 브랜치의 커밋이 모두 현재 브랜치에 들어왔는지 확인한다.
   8. 계획 파일에 `태스크 <N>: 완료 (<커밋 범위>, 리뷰 통과 | 판정 <K>건)`을 남기고 다음 웨이브로 넘어간다.
5. **최종 검증** — 모든 웨이브를 통합한 뒤 `dev-pack:behavior-check`를 따른다. 통과 기준은 호출한 절차가 정한 기준을 그대로 쓴다. 실패하면 원인 영역을 수정 태스크로 정의해 4단계를 한 번 더 돈다.
6. **보고** — 호출한 절차로 돌아가기 전에 다음을 보고한다: 태스크별 커밋, 최종 검증 결과, 계획 파일에 남긴 **판정 전부**(사용자 대신 결정한 사항이므로 하나도 빼지 않는다), 남겨 둔 Minor 지적.

## 유의점

- **계획 파일이 진행 상황의 원본이다.** 컨텍스트가 압축된 뒤에는 기억 대신 계획 파일과 `git log`를 믿는다. 완료로 적힌 태스크를 다시 맡기지 않는다.
- implementer의 커밋이 곧 최종 커밋이다. 호출한 절차의 커밋 단계는 통합된 커밋이 논리 단위로 나뉘었는지 확인하는 것으로 대신한다.
- 태스크 사이에 사용자에게 "계속할까요?"라고 묻지 않는다. 멈추는 경우는 되돌리기 어렵거나 외부에 영향을 주는 작업(마이그레이션·배포·외부 전송), 계획으로 판단할 근거가 없는 충돌, 위 사전 점검의 확인 사항뿐이다.
- push하지 않는다. 워크트리를 지우기 전에는 그 안의 작업이 현재 브랜치에 들어왔는지 반드시 확인한다.
