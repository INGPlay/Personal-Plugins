# 서브에이전트 위임 (Subagent Delegation)

메인 세션은 **오케스트레이터**로서 태스크를 나누고 맡기고 결과를 판정하고 커밋한다. 기능 코드는 직접 쓰지 않는다. 구현은 `dev-pack:implementer`가 하고 검토는 `dev-pack:task-reviewer`가 한다. 메인 컨텍스트에는 계획·판정·커밋 결과만 남기는 것이 목적이다.

implementer는 별도 워크트리 없이 **현재 작업 트리**에서 일한다. 커밋하지 않은 변경, 설치된 의존성, `.env` 같은 설정 파일을 그대로 쓸 수 있기 때문에 준비 비용과 통합 단계가 없다. 대신 작업 트리를 공유하므로 태스크는 기본적으로 **하나씩 순서대로** 실행하고 검증이 서로 독립적이라고 확신할 수 있는 태스크만 병렬로 돌린다.

## 언제 쓰는가

- **쓴다:** 설계 결과 파일 소유가 겹치지 않는 태스크 2개 이상으로 나뉘는 작업. 호출하는 절차들은 이 기준을 따른다.
- **쓰지 않는다:** 한두 파일로 끝나는 작업, 태스크끼리 같은 파일을 계속 주고받아야 하는 작업, 아직 원인을 찾지 못한 버그(원인 추적은 맡기기 전에 태스크를 정할 수 없으므로 메인 세션에서 끝낸 뒤 수정만 맡긴다). 이런 작업은 호출한 절차대로 메인 세션에서 직접 구현한다.

## 절차

1. **사전 점검.** `git status --porcelain`으로 작업 트리 상태를 본다. git 저장소가 아니면 태스크의 변경을 diff로 식별할 수 없으므로 위임하지 않고 메인 세션에서 직접 구현한다.
   - 커밋하지 않은 변경은 implementer에게도 그대로 보이므로 위임을 막지 않는다. 다만 **소유 파일이 될 파일**에 변경이 있으면 그 변경이 태스크의 diff에 섞인다. 2단계에서 소유 파일이 정해지면 이 상태와 대조하고 겹치는 파일이 있으면 3단계 승인 때 먼저 커밋할지 사용자에게 함께 확인한다.
   - 이미 staged된 변경이 있으면 태스크 커밋에 섞여 들어가므로, 위임 전에 unstage할지 먼저 커밋할지 사용자에게 확인한다.
   - 출력 전체를 계획 파일에 **시작 시점 상태**로 적어 둔다. 변경이 있던 파일은 `git hash-object <파일>` 값도 함께 적는다. 상태 줄만으로는 이미 바뀌어 있던 파일을 implementer가 또 고쳤는지 알 수 없기 때문이다. 6단계에서 태스크가 소유 파일 밖을 건드렸는지 이 기록과 비교해 확인한다.
2. **태스크 분해.** 호출한 절차의 탐색·설계 결과를 근거로 태스크를 나누고 세션 스크래치패드(없으면 OS 임시 디렉터리)에 `delegation-<slug>.md`로 계획을 적는다. 태스크마다 다음을 적는다:
   - **목표:** 무엇을 만들거나 바꾸는지 한두 줄로 적는다.
   - **소유 파일:** 이 태스크만 수정하거나 새로 만드는 파일. 다른 태스크와 겹치면 태스크를 합친다.
   - **인터페이스:** 다른 태스크가 의존하는 시그니처·데이터 형태를 정확한 값으로 적는다. 구현자가 추측하게 두지 않는다.
   - **통과 기준과 확인 방법:** 돌려서 확인할 수 있는 형태로 적는다(예: "`npm test -- auth` 초록 + `POST /login`이 401 대신 200"). 기준을 이렇게 적을 수 없으면 태스크가 덜 정의된 것이다. 나누거나 사용자에게 묻는다.
   - **하지 않을 것:** 범위 밖이라 손대면 안 되는 것.

   의존성 추가, lockfile 갱신, 코드 생성, 저장소 전체 포매터 실행처럼 소유 파일 밖까지 바꾸는 작업은 다른 태스크에 섞지 않고 별도 태스크로 떼어 순서상 앞에 둔다. 같은 종류의 작은 수정이 여러 파일에 반복되면 태스크 하나로 묶는다.

   태스크는 의존 관계에 따라 **실행 순서**를 정한다. 기본은 순차 실행이다. 연속한 태스크를 **병렬 묶음**(최대 4개)으로 묶으려면 다음을 모두 만족해야 한다:
   - 서로의 결과에 의존하지 않는다.
   - 각 태스크의 확인 방법이 다른 태스크의 소유 파일을 읽지 않는다. 프로젝트 전체를 컴파일하거나 다른 태스크의 파일을 임포트하는 build·test는 상대가 고치다 만 파일 때문에 깨질 수 있으므로 이 조건을 만족하지 않는다.
   - DB·고정 포트·공유 디렉터리처럼 실행 중에 함께 쓰는 자원이 없다.

   하나라도 확신할 수 없으면 순차로 둔다.
3. **계획 승인.** 실행 순서·병렬 묶음·태스크·통과 기준을 표로 보여 주고 AskUserQuestion으로 승인받는다. 선택지에는 "메인 세션에서 직접 구현"을 함께 둔다. 위임은 태스크마다 리뷰 비용이 들기 때문에 작업이 작으면 직접 하는 편이 낫다. 승인 전에는 구현을 맡기지 않는다. 이 승인이 사용자가 개입하는 주된 지점이다.
4. **태스크 실행.** 순서대로 태스크(또는 병렬 묶음)마다 다음을 반복한다.
   1. `git status --porcelain -- <소유 파일>`이 비어 있는지 확인하고 기준 커밋(`git rev-parse HEAD`)을 계획 파일에 적는다.
   2. `dev-pack:implementer`를 띄운다. 프롬프트에는 그 태스크 항목 전문, 앞 태스크에서 확정된 인터페이스, 저장소의 build·test 명령만 넣는다. 세션의 지난 대화나 다른 태스크의 경과는 넣지 않는다. 모델은 태스크에 맞춰 고른다: 명세가 완전한 기계적 작업은 가벼운 모델, 여러 파일을 엮거나 판단이 필요하면 표준 이상.
      - 순차 실행이면 포그라운드로 띄운다. 권한 확인 창이 사용자에게 그대로 뜬다.
      - 병렬 묶음이면 **한 메시지에서 동시에** 띄운다. 동시에 띄운 implementer는 백그라운드에서 돌기 때문에 권한 확인 창을 띄우지 못하고 허용되지 않은 명령은 바로 거부된다. 프롬프트에 넣은 build·test 명령이 권한 설정에서 허용되어 있는지 먼저 확인하고 허용되어 있지 않으면 사용자에게 허용을 요청하거나 그 묶음을 순차로 돌린다.
   3. 보고를 받으면 상태별로 처리한다. `NEEDS_CONTEXT`는 빠진 정보를 채워 SendMessage로 재개한다. `BLOCKED`는 원인을 보고 맥락 보충, 더 강한 모델로 새로 띄우기, 태스크 분할 중 하나를 고른다. 원인이 권한 거부라면 포그라운드로 다시 띄운다. 같은 조건으로 그대로 다시 시키지 않는다.
   4. `DONE`인 태스크마다 `dev-pack:task-reviewer`를 띄운다. 태스크 항목 전문, 소유 파일 목록, 기준 커밋, implementer의 검증 증거를 넘긴다. 리뷰어에게 특정 지적을 하지 말라고 미리 정해 주지 않는다. 같은 병렬 묶음의 리뷰는 동시에 띄운다.
   5. **수정 루프.** 스펙 ❌이거나 Critical·Important 지적이 있으면 그 지적을 그대로 implementer에게 SendMessage로 보내 고치게 하고 고친 부분만 다시 리뷰받는다. 지적을 보내기 전에 소유 파일을 스크래치패드의 `snapshot-<N>-<회차>/`에 복사해 두고 재검토에는 이전 지적 목록과 그 스냅샷 경로를 넘긴다. Minor 지적은 계획 파일에 적어 두고 루프에 넣지 않는다. 최대 3회까지 돈다. 3회 뒤에도 남은 지적은 오케스트레이터가 판정해 `판정: <결정> — <이유> — <틀렸을 때 비용>` 형식으로 계획 파일에 남긴다. 다음 태스크가 그 위에 쌓이는데 어느 쪽이 맞는지 판단할 근거가 없으면 사용자에게 묻는다. 지적을 조용히 버리지 않으며 메인 세션이 직접 고치지도 않는다. implementer를 재개할 수 없으면 새 implementer를 띄우고 프롬프트에 태스크 항목·지적 목록과 함께 "소유 파일에 이전 구현자의 작업이 남아 있으니 그 위에서 이어서 고쳐라"라고 적는다.
   6. **범위 확인.** `git status --porcelain`을 1단계의 시작 시점 상태와 비교하고 시작 시점에 변경이 있던 파일은 `git hash-object` 값도 대조한다. 같은 병렬 묶음의 소유 파일을 빼고 새로 바뀐 파일이 소유 파일 밖에 있으면 그 변경은 커밋에 넣지 않고 implementer에게 되돌리게 하거나 판정 대상으로 계획 파일에 남긴다.
   7. **검증.** 순차 실행이면 implementer가 일관된 작업 트리에서 통과 기준을 확인했으므로 그 증거로 갈음한다. 수정 루프를 돌았다면 마지막 보고의 검증이 통과 기준 전체를 덮는지 확인하고 덮지 않으면 오케스트레이터가 통과 기준을 직접 돌린다. 병렬 묶음이면 묶음의 모든 태스크가 리뷰를 통과한 뒤 오케스트레이터가 build·test를 한 번 돌린다. 실패 원인이 한 태스크 안에 있으면 그 implementer를 재개해 고치게 한다. 태스크끼리 맞물려 깨졌다면 묶음의 소유 파일을 그대로 소유 파일로 하는 수정 태스크를 새로 정의해 순차로 한 번 더 돈다. 이 수정 태스크는 1번의 빈 상태 확인을 묶음의 소유 파일에서는 건너뛰고 통과하면 묶음의 태스크와 함께 커밋한다.
   8. **커밋.** 리뷰와 검증을 통과한 태스크마다 `dev-pack:commit` 절차로 커밋한다. 커밋 대상은 그 태스크의 소유 파일로 한정하며 시작 시점부터 있던 다른 변경은 스테이징하지 않는다. 병렬 묶음이면 계획에 적은 순서대로 태스크마다 따로 커밋한다.
   9. 계획 파일에 `태스크 <N>: 완료 (<커밋 해시>, 리뷰 통과 | 판정 <K>건)`을 남기고 다음 태스크로 넘어간다.

   태스크를 포기해야 하면 그 태스크의 변경만 되돌린다. 추적 중이던 소유 파일은 `git checkout -- <파일>`로, 새로 만든 소유 파일은 삭제해서 되돌린 뒤 `git status --porcelain -- <소유 파일>`이 비었는지 확인한다. 소유 파일 밖은 건드리지 않는다.
5. **최종 검증.** 모든 태스크를 커밋한 뒤 `dev-pack:behavior-check`를 따른다. 통과 기준은 호출한 절차가 정한 기준을 그대로 쓴다. 실패하면 원인 영역을 수정 태스크로 정의해 4단계를 한 번 더 돈다.
6. **보고.** 호출한 절차로 돌아가기 전에 다음을 보고한다: 태스크별 커밋, 최종 검증 결과, 계획 파일에 남긴 **판정 전부**(사용자 대신 결정한 사항이므로 하나도 빼지 않는다), 남겨 둔 Minor 지적.

## 유의점

- **계획 파일이 진행 상황의 원본이다.** 컨텍스트가 압축된 뒤에는 기억 대신 계획 파일과 `git log`, `git status`를 믿는다. 완료로 적힌 태스크를 다시 맡기지 않는다.
- 오케스트레이터가 만든 태스크별 커밋이 곧 최종 커밋이다. 호출한 절차의 커밋 단계는 커밋이 논리 단위로 나뉘었는지 확인하는 것으로 대신한다.
- 태스크 사이에 사용자에게 "계속할까요?"라고 묻지 않는다. 멈추는 경우는 되돌리기 어렵거나 외부에 영향을 주는 작업(마이그레이션·배포·외부 전송), 계획으로 판단할 근거가 없는 충돌, 위 사전 점검의 확인 사항뿐이다.
- push하지 않는다. 시작 시점부터 있던 사용자의 변경은 되돌리거나 커밋하지 않는다.
