# README Writer

**좋은 README는 멋진 소개문이 아니라, 저장소에 실제로 존재하는 사실을 정리한 문서다.** 방문자(채용 담당자, 협업 후보자, 미래의 나)가 "이게 무슨 프로젝트고, 어떻게 실행하고, 어디부터 보면 되는지"를 몇 초 안에 파악하면 성공이다. 길다고 좋은 게 아니다.

Claude Code 환경이므로 저장소 파일 시스템과 셸에 항상 접근할 수 있다. 사람이 정보를 불러 줄 때까지 기다리지 말고, 도구로 저장소를 직접 읽어 근거를 확보한다.

## 절대 어기면 안 되는 원칙

1. **없는 기능을 지어내지 않는다.** 예시 데이터, 배포 링크, 테스트 명령, Docker 지원, CI 배지는 흔한 템플릿에 으레 들어가 있어 무심코 채우기 쉽다. 저장소에서 근거를 찾지 못한 항목은 넣지 말고, 애매하면 사용자에게 물어본다.
2. **과장하지 않는다.** "혁신적인", "강력한", "완벽한", "최고의" 같은 표현은 오히려 신뢰를 떨어뜨린다. README는 광고가 아니라 사용 안내서다.
3. **실행 명령은 실제 근거에서 가져온다.** `package.json`의 scripts, `Makefile`, 실행 스크립트 등에서 확인해 옮긴다. 확인할 수 없으면 `<!-- 확인 필요 -->`를 남기고 사용자에게 알린다.

## 작업 순서

### 0단계 — 기존 README를 먼저 읽는다

`Glob`으로 `README.md`(또는 `README.rst`, `docs/README.md`)를 찾아 있으면 `Read`로 읽는다. **처음부터 다시 쓰지 않는다.** 사용자가 직접 넣은 배지·스크린샷·데모 링크·고유한 문구는 의도가 담긴 자산이므로 보존한다. 이 스킬의 역할은 그 위에서 (1) 근거 없는 항목 교정, (2) 빠진 표준 섹션 보충, (3) 저장소 현재 상태와 어긋난 부분(바뀐 명령, 삭제된 기능) 갱신이다. 기존 내용을 크게 삭제해야 하면 삭제 전에 이유와 함께 확인받는다.

### 1단계 — 저장소에서 사실부터 모은다

초안 품질은 입력 정보의 정확도에서 갈린다. `Glob`으로 찾고 `Read`로 확인하며, 넓게 훑어야 하면 `Grep`을 쓴다.

- **프로젝트 정체성** — 최상위 폴더 구조, 진입점 파일, 기존 문서·주석. 무엇을 하는 프로젝트인지 한 줄로 정리할 수 있어야 한다.
- **언어·런타임·의존성** — `package.json`, `requirements.txt`, `pyproject.toml`, `pom.xml`, `build.gradle`, `go.mod`, `Cargo.toml`, `Gemfile` 등.
- **실행 방법** — `scripts`, `Makefile`, `Dockerfile`, `docker-compose.yml`, 셸/배치 스크립트, 프레임워크 실행 명령.
- **환경 변수·설정** — `.env.example`, config 파일. 실제로 필요한 키만 추린다.
- **폴더 구조** — 어디부터 보면 되는지 안내할 수 있도록 주요 디렉터리의 역할.

`Bash`로는 부작용 없는 확인만 실행해 근거를 굳힌다:

- 클론 URL은 `git remote get-url origin`으로 확인해 자리표시자 대신 실제 값을 넣는다. 리모트가 없으면 자리표시자를 유지한다.
- 라이선스 섹션은 `LICENSE` 파일이 있을 때만 넣고, 내용에서 종류를 확인한다.
- CI 배지·테스트 언급은 `.github/workflows/` 같은 실제 설정이 있을 때만 한다.
- 빌드·배포·DB 마이그레이션처럼 상태를 바꾸는 명령은 실행하지 말고, 파일 근거로만 확인한 뒤 사용자에게 직접 돌려보길 권한다.

저장소를 다 읽고도 사실로 채울 수 없는 빈칸(프로젝트 목적이 코드만으로 불분명하거나, 지원/예정/실험 기능의 경계가 애매할 때)이 남으면 흔한 예시로 메우지 말고 `AskUserQuestion`으로 꼭 필요한 것만 묻는다.

### 2단계 — 표준 구조로 초안을 작성한다

해당하지 않는 섹션은 억지로 채우지 말고 **뺀다**(환경 변수가 없으면 설정 섹션 생략). 새 초안은 같은 스킬 폴더의 `assets/README_template.md`를 `Read`로 열어 참고한다. (플러그인으로 설치된 경우 경로는 `${CLAUDE_PLUGIN_ROOT}/skills/readme-writer/assets/README_template.md`.)

1. **프로젝트 소개** — 해결하려는 문제와 대상 사용자를 한두 문단으로. 소개가 길어지면 정작 중요한 실행 방법이 아래로 밀린다.
2. **빠른 시작 (Quick Start)** — 클론 → 의존성 설치 → 실행 순서대로. 초보 개발자가 이 섹션만 보고도 실행할 수 있어야 한다. 설치 단계와 실행 예시는 분리한다.
3. **주요 기능** — 이름 나열이 아니라 "사용자가 실제로 얻는 결과" 중심으로(예: "게시글 초안 생성", "파일 기반 입력 처리"). 구현 상태가 갈리면 지원/예정/실험 중을 정직하게 구분한다.
4. **설정과 주의사항** — 환경 변수, API 키, 운영체제 차이(Windows/Unix 경로·명령), 알려진 제한 사항.

폴더 구조·라이선스·기여 방법은 실제 근거가 있을 때만 추가한다.

### 3단계 — 검증하고 군더더기를 덜어낸다

- 각 기능·명령·항목이 저장소의 실제 근거와 연결되는가? 근거 없는 항목은 삭제했거나 `<!-- 확인 필요 -->`로 표시했는가?
- 과장 형용사가 남아 있지 않은가?
- 설치·실행 명령이 실제 파일과 일치하는가?
- 소개가 실행 방법보다 무겁지 않은가?

마지막으로 확실히 검증하지 못한 부분(특히 설치·실행 명령)은 사용자에게 짚어 주고 한 번 직접 돌려보길 권한다.

## 출력 형식

- 저장소 루트의 `README.md`에 `Write`(신규) 또는 `Edit`(기존 갱신)로 **직접 쓴다.** 채팅에 마크다운만 뿌리고 끝내지 않는다. 작성 후 무엇을 새로 채웠고 무엇을 `<!-- 확인 필요 -->`로 남겼는지 요약한다.
- 본문 언어는 프로젝트 성격과 사용자 선호를 따르고, 지정이 없으면 사용자가 대화에서 쓰는 언어에 맞춘다.
- 코드·명령 블록에는 언어를 명시한 코드 펜스(bash, json, python 등)를 쓴다.
