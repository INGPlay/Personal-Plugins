# 리팩터링 (Refactoring)

**동작은 그대로 두고 내부 구조만 개선**하는 절차. 기능 개발·버그 수정과 정반대로, 새 동작을 추가하지 않는 것이 규칙이다. 리팩터링의 안전성은 "변경 전후 동작이 같음을 증명할 수 있는가"에서 나온다.

## 원칙

- **동작 보존.** 리팩터링 커밋에 기능 추가·버그 수정을 섞지 않는다. 리팩터링 중 버그를 발견하면 따로 표시하고 별도 커밋/작업으로 분리한다.
- **작은 스텝.** 큰 변경 하나보다, 각 단계마다 동작이 유지되는 작은 변경 여러 개가 안전하다.

## 절차

1. **코드베이스 탐색** — `dev-pack:codebase-exploration` 스킬을 따른다. 대상 코드의 책임·경계와 **호출하는 쪽(참조)**을 파악한다. 그 스킬의 흐름 추적 절차대로 영향 범위를 반드시 확인한다.
2. **안전망 확보** — 변경 전, 동작을 고정할 수단을 마련한다. 기존 테스트가 있으면 먼저 돌려 초록인지 확인하고, 없으면 현재 동작을 포착하는 특성화 테스트(characterization test)를 추가한다. 안전망 없이 큰 리팩터링을 시작하지 않는다.
3. **변경** — 구조를 개선한다(이름 변경·추출·중복 제거·이동 등). 한 번에 한 종류의 변경만 한다. 1단계에서 파악한 참조는 하나도 빠뜨리지 않고 함께 고치고, 변경 후 Grep으로 깨지거나 남은 참조가 없는지 확인한다.
4. **동작 동일 확인** — `dev-pack:behavior-check` 스킬을 따른다. 통과 기준은 하나다: **2단계 안전망이 변경 전과 똑같이 초록일 것.** 여기서는 각 스텝마다 돌린다 — 마지막에 한 번이 아니다. 결과가 달라졌다면 그건 리팩터링이 아니라 회귀다 — 되돌리고 원인을 찾는다.
   **문제가 나오면 3단계로 돌아가 고치고 다시 확인한다. 안전망이 초록이 될 때까지 3~4단계를 반복한다.**
5. **커밋** — 동작이 동일함을 확인했으면 `dev-pack:commit` 스킬로 커밋한다(`refactor:` 타입). 안전망으로 추가한 테스트는 `test:`로 분리해도 좋다.
6. **코드 리뷰 인계** — 커밋까지 끝냈으면 **사용자에게 `/code-review` 실행을 요청하며 마무리한다.** 이 스킬은 사용자만 호출할 수 있어 Claude가 대신 돌릴 수 없다. 안전망이 변경 전과 동일하게 초록이라는 확인과 무엇을 어떻게 옮겼는지 한 줄로 요약해 함께 전달하고, **"동작 변화가 없는가"를 특히 봐 달라고 짚어 준다.** 구조에 대한 지적은 고쳐서 반영하되, **리뷰가 버그를 찾아냈다면 리팩터링 커밋에 섞지 말고 별도 `fix:` 커밋으로 분리한다**(위 동작 보존 원칙). 지적이 HEAD 커밋 하나에만 걸려 있고 아직 push하지 않았다면 `--amend`로 합쳐도 되며, 어느 쪽으로 할지는 사용자에게 확인한다. **push는 사용자가 명시할 때만 하고, 리뷰 전이라면 아직 리뷰를 받지 않은 커밋임을 먼저 알린다** — push한 뒤에는 `--amend`를 쓰지 않는다.

## 유의점

- 테스트가 전혀 없고 추가도 어려운 코드라면, 리스크를 사용자에게 알리고 범위를 좁히거나 수동 검증 방법을 합의한 뒤 진행한다.
- 동작을 바꿔야 하는 개선이라면 그것은 리팩터링이 아니다 — 기능 개발/기능 변경/버그 수정 절차로 전환한다.
