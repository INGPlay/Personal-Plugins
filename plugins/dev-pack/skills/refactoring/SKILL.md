# 리팩터링 (Refactoring)

**동작은 그대로 두고 내부 구조만 개선**하는 절차. 기능 개발·버그 수정과 정반대로, 새 동작을 추가하지 않는 것이 규칙이다. 리팩터링의 안전성은 "변경 전후 동작이 같음을 증명할 수 있는가"에서 나온다.

## 원칙

- **동작 보존.** 리팩터링 커밋에 기능 추가·버그 수정을 섞지 않는다. 리팩터링 중 버그를 발견하면 따로 표시하고 별도 커밋/작업으로 분리한다.
- **작은 스텝.** 큰 변경 하나보다, 각 단계마다 동작이 유지되는 작은 변경 여러 개가 안전하다.

## 절차

1. **코드베이스 탐색** — `dev-pack:codebase-exploration` 스킬을 따른다. 대상 코드의 책임·경계와 **호출하는 쪽(참조)**을 파악한다. serena의 `find_referencing_symbols`로 영향 범위를 반드시 확인한다.
2. **안전망 확보** — 변경 전, 동작을 고정할 수단을 마련한다. 기존 테스트가 있으면 먼저 돌려 초록인지 확인하고, 없으면 현재 동작을 포착하는 특성화 테스트(characterization test)를 추가한다. 안전망 없이 큰 리팩터링을 시작하지 않는다.
3. **변경** — 구조를 개선한다(이름 변경·추출·중복 제거·이동 등). serena의 `rename_symbol`·심볼 편집처럼 참조까지 안전하게 바꿔 주는 도구를 우선 사용한다. 한 번에 한 종류의 변경만 한다.
4. **동작 동일 확인** — 각 스텝마다 테스트·build를 돌려 동작이 그대로인지 확인한다. `/verify`·`/run`으로 실제 동작도 점검한다. 결과가 달라졌다면 그건 리팩터링이 아니라 회귀다 — 되돌리고 원인을 찾는다.
5. **코드 리뷰** — `/code-review`로 검토한다. "동작 변화가 없는가"를 특히 본다.
6. **추가 수정** — 지적을 반영하고 **4~6단계를 통과할 때까지 반복**한다(수정 후 재검증).
7. **커밋** — `dev-pack:commit` 스킬로 커밋한다(`refactor:` 타입). 안전망으로 추가한 테스트는 `test:`로 분리해도 좋다. push는 사용자가 명시할 때만.

## 유의점

- 테스트가 전혀 없고 추가도 어려운 코드라면, 리스크를 사용자에게 알리고 범위를 좁히거나 수동 검증 방법을 합의한 뒤 진행한다.
- 동작을 바꿔야 하는 개선이라면 그것은 리팩터링이 아니다 — 기능 개발/버그 수정 절차로 전환한다.
