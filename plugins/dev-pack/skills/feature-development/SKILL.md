# 기능 개발 (Feature Development)

코드베이스에 없던 동작을 새로 추가하는 표준 절차. 무작정 코드부터 쓰지 않고, 이해하고 → 만들고 → 돌려보고 → 검토하고 → 다듬는 순서를 지킨다.

## 절차

1. **코드베이스 탐색** — `dev-pack:codebase-exploration` 스킬을 따른다. 기존 패턴·유사 구현·확장 지점을 파악하고, 새 코드를 어디에 어떻게 붙일지 후보를 잡는다.
2. **설계 (큰 기능만)** — 파일이 여러 개 걸치거나 데이터 구조·인터페이스를 새로 정하는 규모라면, 코드 작성 전에 접근 방식을 먼저 정한다. 한 줄~한 파일 수준의 작은 기능이면 이 단계는 건너뛴다. 설계가 불확실하면 진행 전 사용자에게 방향을 확인한다.
3. **코드 작성** — 주변 코드의 관례(명명·주석 밀도·구조)에 맞춰 구현한다. 외부 라이브러리 API가 헷갈리면 추측하지 말고 context7로 확인한다.
4. **검증** — 읽어서 맞는 것과 실제로 도는 것은 다르다. build/lint/test를 돌리고, 가능하면 실제 동작을 확인한다. 기본 제공 `/verify`·`/run` 스킬을 활용하고, 웹 UI라면 playwright로 실제 흐름을 구동해 본다.
5. **코드 리뷰** — `/code-review`로 변경분을 검토한다. 보안이 민감한 변경이면 `/security-review`도 함께 돌린다.
6. **추가 수정** — 검증·리뷰에서 나온 문제를 고친다. **4~6단계는 통과할 때까지 반복한다** (수정 후에는 반드시 다시 검증·리뷰). 한 번에 끝난다고 가정하지 않는다.
7. **커밋** — 통과하면 `dev-pack:commit` 스킬로 커밋한다(conventional commit, 논리 단위별 분리). push는 사용자가 명시할 때만 한다.

## 유의점

- 4~6은 루프다. 리뷰 지적을 반영하면 검증이 다시 필요하다 — 지적만 고치고 바로 커밋하지 않는다.
- 요청 범위를 넘는 리팩터링·기능을 임의로 끼워 넣지 않는다. 곁가지로 발견한 개선점은 별도로 제안한다.
- 되돌리기 어렵거나 외부에 영향을 주는 작업(마이그레이션·배포·외부 전송)은 실행 전 확인한다.
