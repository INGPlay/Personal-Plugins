# 기능 개발 (Feature Development)

코드베이스에 없던 동작을 새로 추가하는 표준 절차. 무작정 코드부터 쓰지 않고, 이해하고 → 만들고 → 돌려보고 → 커밋하는 순서를 지킨다. 코드 리뷰는 마지막에 사용자가 돌린다.

## 절차

1. **코드베이스 탐색** — `dev-pack:codebase-exploration` 스킬을 따른다. 기존 패턴·유사 구현·확장 지점을 파악하고, 새 코드를 어디에 어떻게 붙일지 후보를 잡는다.
2. **설계 (큰 기능만)** — 파일이 여러 개 걸치거나 데이터 구조·인터페이스를 새로 정하는 규모라면, 코드 작성 전에 접근 방식을 먼저 정한다. 한 줄~한 파일 수준의 작은 기능이면 이 단계는 건너뛴다. **접근 방식이 여러 갈래로 갈리면 임의로 정하지 말고, 코드를 쓰기 전에 AskUserQuestion으로 방향을 확인한다.**
3. **코드 작성** — 주변 코드의 관례(명명·주석 밀도·구조)에 맞춰 구현한다. 외부 라이브러리 API가 헷갈리면 추측하지 말고 context7로 확인한다.
4. **검증** — 먼저 **통과 기준을 한 줄로 못박는다**(예: "X 테스트 초록 + 화면에서 Y 동작"). 읽어서 맞는 것과 실제로 도는 것은 다르다. build/lint/test를 직접 돌리고, `/run`으로 앱을 띄워 실제 동작을 본다(웹 UI면 playwright). DB·환경변수·다단계 빌드 때문에 `/run`이 앱을 못 띄우면 `/run-skill-generator`로 실행 레시피를 만들어 두도록 사용자에게 권한다. 보안이 민감한 변경이면 `/security-review`도 직접 실행한다(호출 가능).
   **문제가 나오면 3단계로 돌아가 고치고 다시 검증한다. 통과 기준을 만족할 때까지 3~4단계를 반복한다.**
5. **커밋** — 검증을 통과하면 `dev-pack:commit` 스킬로 커밋한다(conventional commit, 논리 단위별 분리).
6. **코드 리뷰 인계** — 커밋까지 끝냈으면 **사용자에게 `/code-review` 실행을 요청하며 마무리한다.** 이 스킬은 사용자만 호출할 수 있어 Claude가 대신 돌릴 수 없다. 무엇을 바꿨고 어떤 검증을 통과했는지 한 줄로 요약해 함께 전달한다. 지적이 나오면 고친 뒤 **별도 커밋으로 남기는 것을 기본으로 한다.** 지적이 HEAD 커밋 하나에만 걸려 있고 아직 push하지 않았다면 `--amend`로 합쳐도 되며, 어느 쪽으로 할지는 사용자에게 확인한다. **push는 사용자가 명시할 때만 하고, 리뷰 전이라면 아직 리뷰를 받지 않은 커밋임을 먼저 알린다** — push한 뒤에는 `--amend`를 쓰지 않는다.

## 유의점

- 3~4는 루프다. 검증에 실패한 채로 커밋하지 않는다. build/lint/test가 초록인 것만으로 "동작한다"고 단정하지 말고, 4단계에서 못박은 통과 기준을 실제로 만족했는지 본다.
- 요청 범위를 넘는 리팩터링·기능을 임의로 끼워 넣지 않는다. 곁가지로 발견한 개선점은 별도로 제안한다.
- 되돌리기 어렵거나 외부에 영향을 주는 작업(마이그레이션·배포·외부 전송)은 실행 전 확인한다.
