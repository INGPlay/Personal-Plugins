# 동작 확인 (Behavior Check)

바꾼 코드가 **의도대로 실제로 도는지** 돌려서 확인한다. 커밋 직전의 마지막 관문이다. 코드를 읽고 판단하는 `/code-review`와 달리, 여기서는 직접 실행한 결과만 근거로 삼는다.

## 원칙

- **읽어서 맞는 것과 실제로 도는 것은 다르다.** 코드를 눈으로 훑고 "맞다"고 판단하지 않는다. 직접 돌린다.
- **초록이 곧 동작은 아니다.** build/lint/test가 통과했다는 것은 통과 기준의 일부일 뿐이다. 못박은 기준을 실제로 만족했는지 따로 본다.
- **실패를 숨기지 않는다.** 통과하지 못한 채 커밋하지 않고, 통과했다고 보고하지도 않는다.

## 절차

1. **통과 기준 못박기** — 검증을 시작하기 전에 무엇이 만족되어야 "됐다"인지 **한 줄로 적는다**(예: "X 테스트 초록 + 화면에서 Y 동작"). 호출한 절차 스킬이 기준을 정해 줬다면 그것을 쓴다. 기준 없이 시작하면 어디서 멈춰야 할지 알 수 없다.
2. **자동 검사** — 프로젝트의 build·lint·test를 **직접 실행한다**. 명령은 추측하지 말고 `package.json` 스크립트·Makefile·CI 설정 등 저장소의 실제 정의에서 확인한다. 관련 테스트만 골라 돌렸다면 마지막에는 전체를 한 번 돌려 다른 곳이 깨지지 않았는지 본다.
3. **실제 동작 확인** — `/run`으로 앱을 띄워 눈으로 본다(웹 UI면 playwright). DB·환경변수·다단계 빌드 때문에 `/run`이 앱을 못 띄우면, `/run-skill-generator`로 실행 레시피를 만들어 두도록 사용자에게 권한다. 실행 자체가 불가능한 변경(라이브러리 내부 등)이면 테스트가 이 단계를 대신하며, 그 사실을 보고에 남긴다.
4. **보안 점검 (해당할 때)** — 인증·권한·입력 처리·비밀값·외부 입력을 다뤘다면 `/security-review`도 직접 실행한다(Claude가 호출할 수 있다).
5. **판정과 루프** — 1단계 기준을 항목별로 대조한다.
   - **실패했으면 호출한 절차의 코드 작성·수정 단계로 돌아간다.** 고친 뒤 2단계부터 다시 돈다. 기준을 만족할 때까지 반복한다.
   - 통과했으면 무엇을 어떻게 확인했는지(돌린 명령, 본 동작) 한 줄로 요약해 다음 단계로 넘긴다.

## 유의점

- 검증이 실패했는데 통과 기준을 낮추는 방향으로 대응하지 않는다. 기준이 애초에 틀렸다고 판단되면 사용자에게 알리고 합의한다.
- 테스트가 실패할 때 코드가 문제인지 테스트가 문제인지 매번 구분한다. 테스트를 고쳐 초록을 만드는 것은 그 테스트가 낡았다고 **판단한 근거가 있을 때만** 한다.
- 검증 중 발견한 무관한 문제는 고치지 말고 따로 보고한다.
- `/code-review`는 검증 단계에 포함되지 않는다. 사용자만 호출할 수 있으며, 커밋 이후에 사용자가 실행한다.

## 다른 절차와의 연결

기능 개발·기능 변경·버그 수정·리팩터링 절차에서 코드 작성 다음, 커밋 직전 단계로 호출된다. **통과 기준은 절차마다 다르며 호출하는 쪽이 정한다** — 각 절차 스킬의 검증 단계에 적혀 있으므로 여기에 옮겨 적지 않는다. 단독으로 호출되어 받은 기준이 없으면 1단계에서 직접 정의한다.
