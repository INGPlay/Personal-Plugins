# 코드베이스 탐색 (Codebase Exploration)

수정을 시작하기 전에 **정확한 지도**를 먼저 확보한다. 추측으로 코드를 짜다가 뒤엎는 것을 막는 것이 이 절차의 목적이다. 이 스킬은 다른 개발 절차(기능 개발·버그 수정·리팩터링)의 공통 1단계이기도 하다.

## 원칙

- **코드를 수정하지 않는다.** 목적은 이해이지 변경이 아니다. 변경이 필요하면 해당 절차 스킬로 넘어간다.
- **추측 대신 근거.** "아마 여기일 것"으로 멈추지 말고 도구로 실제 정의·참조를 확인한다.
- **넓게 훑을 땐 위임.** 여러 디렉터리·명명 규칙을 동시에 뒤져야 하면 `Explore`/`Task` 서브에이전트로 팬아웃하고 결론만 받는다.

## 도구 활용

- **serena** — 심볼 단위 탐색이 핵심. `find_symbol`로 정의를 찾고, `find_referencing_symbols`로 "이걸 누가 쓰는지"(영향 범위)를 추적하고, `get_symbols_overview`로 파일 골격을 본다. 텍스트 grep보다 정확하다.
- **Grep / Glob** — 키워드·파일 패턴으로 진입점을 잡을 때. 심볼을 특정하기 전 단계.
- **context7** — 외부 라이브러리·프레임워크가 얽혀 있으면 기억에 의존하지 말고 현재 문서를 조회해 실제 API·동작을 확인한다.
- **Read** — 후보를 좁힌 뒤 해당 부분만 정독한다.

## 절차

1. **범위 잡기** — 무엇을 이해해야 하는지 한 줄로 정의한다(수정 지점 찾기 / 흐름 파악 / 영향도 분석 중 무엇인지).
2. **진입점 찾기** — Grep/Glob으로 관련 키워드·파일을 찾고, serena로 핵심 심볼의 정의를 연다.
3. **흐름 추적** — 호출 관계와 데이터 흐름을 따라간다. `find_referencing_symbols`로 상류(누가 호출하나)와 하류(무엇을 호출하나)를 모두 본다.
4. **의존성 확인** — 외부 라이브러리가 관여하면 context7로 실제 API를 확인한다. 내부 모듈 경계·설정·부작용(파일/네트워크/DB)도 파악한다.
5. **요약** — 다음을 정리해 보고한다:
   - 관련 파일·심볼 (`file_path:line` 형식으로 클릭 가능하게)
   - 제어/데이터 흐름 요약
   - 수정한다면 손대야 할 지점 후보
   - 리스크·주의점(숨은 의존성, 테스트 공백, 부작용)

## 다른 절차와의 연결

이 스킬은 보통 단독으로도 쓰이지만, 기능 개발·버그 수정·리팩터링 절차에서 1단계로 호출된다. 그 경우 5단계의 "수정 지점 후보"가 다음 단계(작성/수정)의 입력이 된다.
